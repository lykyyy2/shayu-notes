# 坑三：乱码不是乱码，是念它的方式错了

## 场景

用 PowerShell 调一个返回 JSON 的公开 API，中文全是 `ç¥žç§˜å°ç¢Žæ¥`。

第一反应：控制台编码不对。设 `[Console]::OutputEncoding = UTF8`，重跑——还是乱码。

第二反应：写文件时编码不对。改成 `[System.IO.File]::WriteAllLines($p, $lines, UTF8Encoding)`——还是乱码。

## 真因

乱码发生在**更早一步**。

`Invoke-RestMethod` 在响应头没有正确 charset 时，会按 Latin-1 去解那堆 UTF-8 字节。
字符串在内存里就已经错了——后面怎么输出、怎么写文件，都救不回来。

你拿着一个已经念错的字符串，再怎么大声念，念出来的还是错的。

## 正解

不要让它解，自己解：

```powershell
$resp  = Invoke-WebRequest -Uri $url -UseBasicParsing
$bytes = $resp.RawContentStream.ToArray()
$json  = [System.Text.Encoding]::UTF8.GetString($bytes) | ConvertFrom-Json
```

拿原始字节，自己按 UTF-8 解码。

## 同一天里的另一半

同一台机器上，`Get-Content` 读一个 UTF-8 文件，也出乱码——因为它按系统代码页（GBK）念的。

**字节没错，是念它的方式错了。** 同一个病，两副面孔：

| 症状 | 真实原因 |
|---|---|
| 控制台打印中文乱码 | 输出编码 |
| 写进文件还是乱码 | 内存里就已经错了 |
| 读文本文件乱码 | 读的时候按错了代码页 |

**排错顺序：先怀疑"读进来那一步"，再怀疑"写出去那一步"。** 大多数人（包括我）反着来。

## 教训

1. 乱码先定位在哪一层坏的：传输 / 解码 / 输出 / 落盘。**逐层验，别跳。**
2. 看见"乱码"两个字，不要立刻改输出设置——先想想它是不是在解码那一步就已经坏了。
3. HTTP 响应永远自己按字节解，不要相信库的默认猜测。

## 一句能带走的话

> 乱码不是乱码。是有人用错的读法，念了对的字。
